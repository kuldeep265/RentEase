4 System Architecture & Database Design

1. The Django MVT Pattern

Django implements the Model-View-Template (MVT) design pattern:

Model (properties/models.py)

The single source of truth for your data. Defines table schemas, field types, constraints (e.g. MinValueValidator), and custom methods like get_amenities_list().

View (properties/views.py)

The controller logic. Intercepts incoming HttpRequest, performs authentication and authorization checks, queries the ORM, and returns an HttpResponse or redirect.

Template (templates/*.html)

The presentation layer. Uses the Django Template Language (DTL) for template inheritance ({% extends 'base.html' %}), loops ({% for %}), and safe variable interpolation.

5 Top 30 Viva Questions & In-Depth Answers

Category A: Django Framework & Core Architecture

Q1: What is Django and why did you choose it over Flask or Node.js? Fundamental
Answer: Django is a high-level, batteries-included Python web framework designed for rapid and secure web development. We chose Django over Flask or Express because it includes built-in Object-Relational Mapping (ORM), robust user authentication, an automatic Admin interface, automated CSRF protection, and standardized directory structure out of the box, significantly reducing boilerplate code and security risks.
Q2: What is the difference between MVC and MVT in Django? Fundamental
Answer: In traditional MVC (Model-View-Controller), the Controller handles user requests and dispatches data between Model and View. In Django's MVT (Model-View-Template):
  • Model: Maps data structures to database tables (same as in MVC).
  • View: Acts like the Controller in MVC; it processes requests, executes business logic, queries models, and selects templates.
  • Template: Acts like the View in MVC; it produces the visual HTML output rendered to the client. The Django framework itself acts as the overarching controller routing URLs to views.
Q3: What is the purpose of manage.py, settings.py, urls.py, and wsgi.py? Fundamental
Answer:
  • manage.py: CLI management script to run the local server, create migrations, execute test suites, and run custom management commands.
  • settings.py: The centralized configuration file containing installed apps, database credentials, middleware, auth redirects, static/media paths, and security flags.
  • urls.py: The master routing table mapping URL patterns to view functions using path().
  • wsgi.py: Web Server Gateway Interface entry point used by production web servers (e.g. Gunicorn/uWSGI) to serve the application.
Q4: What is the difference between a Django Project and a Django App? Fundamental
Answer: A Project represents the entire website configuration (in our case, rentease), containing settings, master URLs, and WSGI handlers. An App is a self-contained, modular Python package that handles a specific domain of functionality (in our case, properties), containing its own models, views, forms, and tests. A single project can house multiple apps.
Q5: Explain the HTTP Request-Response lifecycle in your application. Intermediate
Answer:
  1. The client browser sends an HTTP request to the web server.
  2. Django's middleware stack processes the request (security checks, session decoding, user authentication).
  3. The URL dispatcher in urls.py matches the request path with configured patterns.
  4. The matching view function in views.py executes (handling GET/POST, querying ORM models).
  5. The view renders a template or issues an HttpResponseRedirect.
  6. Response middlewares process headers and cookies, returning the final HTTP response to the browser.

Category B: Models, Database & Django ORM

Q6: What is an ORM and what are its benefits? Fundamental
Answer: An Object-Relational Mapper (ORM) allows developers to interact with relational databases using object-oriented Python code instead of raw SQL queries. Benefits include: database engine portability (switch from SQLite to PostgreSQL without rewriting queries), automatic protection against SQL injection via parameterized queries, type validation, and clean relationship management through model properties.
Q7: What does on_delete=models.CASCADE mean in your models? Intermediate
Answer: In properties/models.py, Property.owner uses on_delete=models.CASCADE. This specifies that if a User record is deleted from the database, all Property listings owned by that user will automatically be deleted to prevent orphaned records. Similarly, deleting a Property cascades to delete its associated Booking requests.
Q8: What is the difference between makemigrations and migrate? Fundamental
Answer:
  • python manage.py makemigrations: Inspects changes made in models.py and writes human-readable migration blueprint files in the migrations/ directory without modifying the actual database tables.
  • python manage.py migrate: Executes the pending migration files against the database, running the corresponding CREATE TABLE or ALTER TABLE SQL statements.
Q9: How did you implement search and filtering using the ORM? Intermediate
Answer: In property_list view (views.py), we chain Django ORM filter lookups based on GET parameters: properties = Property.objects.filter(is_available=True)
If a location is passed: properties.filter(location__icontains=location) (case-insensitive substring matching).
If max rent is passed: properties.filter(rent__lte=float(max_rent)) (less than or equal to).
Django ORM querysets are lazy; they are not evaluated against the database until iterated over in the template or paginator.
Q10: What is the difference between auto_now and auto_now_add? Fundamental
Answer: auto_now_add=True sets the timestamp only once when the object is first created (used for created_at).
auto_now=True updates the timestamp to the current time every time save() is called on the object (used for updated_at).

Category C: Views, Forms & HTTP Methods

Q11: Why did you use Function-Based Views (FBVs) over Class-Based Views (CBVs)? Intermediate
Answer: Function-Based Views provide explicit, readable, step-by-step control over the HTTP request flow. In an academic examination setting, FBVs demonstrate an understanding of HttpRequest objects, manual form validation, explicit redirects, message dispatching, and fine-grained access checks without hiding logic behind complex multi-inheritance class mixins.
Q12: What is the POST-Redirect-GET (PRG) pattern and why is it important? Advanced
Answer: The PRG pattern is a web development design pattern that prevents duplicate form submissions. When a user submits a form via POST (e.g. adding a property or booking), the server processes the data, saves it, and immediately returns an HTTP 302 Redirect (GET) to another URL (like the dashboard or detail page). If the user subsequently refreshes the page, their browser re-requests the GET URL rather than re-submitting the POST data, avoiding duplicate database entries.
Q13: What is the difference between forms.Form and forms.ModelForm? Fundamental
Answer: forms.Form is a generic form where you manually declare each field, its type, and its validation.
forms.ModelForm is directly tied to a Django Model via an inner class Meta. It automatically generates form fields, widget types, labels, and validation rules based on the model's database definitions, and provides a save() method to persist data directly.
Q14: How does get_object_or_404() work? Fundamental
Answer: get_object_or_404(Model, pk=pk) calls Model.objects.get(pk=pk). If the record exists, it returns the instance. If the record does not exist, instead of raising an unhandled Model.DoesNotExist 500 server error, it cleanly raises a django.http.Http404 exception, returning a standard 404 Not Found response to the user.
Q15: How did you implement custom form validation in forms.py? Intermediate
Answer: In BookingForm, we implemented clean_start_date() to ensure the selected move-in date is not in the past: if start_date < timezone.now().date(): raise forms.ValidationError("Move-in date cannot be in the past."). Django automatically executes field-specific clean_<field_name>() methods during form.is_valid().

Category D: Security, Authentication & Permissions

Q16: How does CSRF protection work in Django? Advanced
Answer: Cross-Site Request Forgery occurs when a malicious site tricks an authenticated user's browser into executing an unwanted action on another site. Django defends against this using the Synchronizer Token Pattern:
  1. Django sets a cryptographically secure random token in a cookie.
  2. When rendering forms, {% csrf_token %} injects a hidden input containing this token.
  3. On POST requests, CsrfViewMiddleware compares the form token with the cookie value. If they do not match or the token is missing, the request is rejected with an HTTP 403 Forbidden.
Q17: What does the @login_required decorator do? Fundamental
Answer: The @login_required decorator wraps a view function and checks request.user.is_authenticated. If the user is logged in, the view executes normally. If anonymous, Django automatically redirects the browser to LOGIN_URL (/accounts/login/) with a query parameter ?next=<current_path> so that upon successful login, the user is redirected back to their intended page.
Q18: How do you prevent User A from editing or deleting User B's property? Advanced
Answer: We enforce backend authorization checks in edit_property and delete_property views: 
if property.owner != request.user:
    messages.error(request, "You do not have permission to modify this property.")
    return redirect('property_detail', pk=pk)
We never rely merely on hiding the "Edit" button in HTML templates, because an attacker could still forge a direct POST or URL request. Enforcing it in the view completely eliminates Insecure Direct Object Reference (IDOR) vulnerabilities.
Q19: How are passwords stored and verified in Django? Intermediate
Answer: Passwords are never stored in plain text. Django hashes them using the **PBKDF2 algorithm with a SHA-256 hash**, incorporating a unique cryptographic salt and thousands of hashing iterations. When a user logs in, Django hashes the provided password with the stored salt and compares the resulting hash; the original plain-text password cannot be decrypted even if the database is exposed.
Q20: How does Django protect against Cross-Site Scripting (XSS)? Intermediate
Answer: Django's Template Language automatically HTML-escapes all dynamic variables by default (converting < to &lt;, > to &gt;, quotes, and ampersands). This prevents malicious JavaScript submitted in form fields (like property descriptions or titles) from executing in another user's browser.

Category E: Frontend, Media & Static Files

Q21: What is the difference between STATIC files and MEDIA files in Django? Fundamental
Answer:
  • STATIC files (STATIC_URL, STATICFILES_DIRS): Static assets shipped with the codebase created by developers (CSS styles, JavaScript files, static UI logos, background illustrations).
  • MEDIA files (MEDIA_URL, MEDIA_ROOT): Dynamic user-uploaded content created during runtime (e.g. photos uploaded by owners when adding properties via ImageField).
Q22: How does template inheritance work in base.html? Fundamental
Answer: base.html defines the global skeletal structure of the site (HTML head, custom CSS, navbar, alerts container, and footer) with placeholder tags like {% block content %}{% endblock %}. Child templates use {% extends 'base.html' %} and inject page-specific markup inside matching blocks, avoiding code duplication and ensuring consistent styling across all pages.
Q23: How did you implement pagination for properties? Intermediate
Answer: We used Django's built-in Paginator class in properties/views.py: paginator = Paginator(properties, 6) (6 properties per page). We extract the current page via request.GET.get('page') and pass page_obj to the template. The template then renders Previous, Page Number, and Next links while preserving any active filter query parameters.

Category F: Testing & Quality Assurance

Q24: What is the purpose of automated testing in Django and what did your 39 tests cover? Intermediate
Answer: Automated tests in properties/tests.py subclass django.test.TestCase to execute against a clean, isolated in-memory test database that is torn down after execution. Our 39 unit tests cover:
  • Public view availability (HTTP 200 on Home, About, Contact, Property List).
  • Search filtering logic (matching keywords and budget thresholds).
  • Authentication flows (registration, valid and invalid logins).
  • Access control (ensuring unauthenticated users cannot access owner dashboard or booking actions).
  • Ownership enforcement (verifying non-owners cannot edit or delete properties).
  • Booking lifecycle (submission, cancellation, and owner approval/rejection state transitions).
  • Verified review permissions (ensuring unbooked users and owners cannot review, while booked tenants can rate and update).
Q25: What command do you run to execute tests and what does OK signify? Fundamental
Answer: Run python manage.py test. Django creates an isolated test database, runs all 39 test methods across test classes, outputs a dot . for every passing test, prints execution time, and outputs OK indicating zero failures and zero errors before automatically destroying the test database.

Category G: Rating, Reviews & Trust Architecture

Q26: How does the Rating and Review feature prevent fake reviews? Advanced
Answer: RentEase enforces a strict backend booking-verification check: Booking.objects.filter(property=property, tenant=request.user).exists(). Only tenants who have actually submitted a booking for that property can submit reviews. Furthermore, owners cannot review their own properties (property.owner == request.user), and the unique_together = ('property', 'tenant') database constraint ensures each tenant can leave only one review per property (updating it if resubmitted).
Q27: How is the average property rating computed and rendered dynamically? Intermediate
Answer: Rather than storing a redundant rating column that can become out of sync, the Property model exposes dynamic methods: average_rating() (which calculates the mean star value rounded to 1 decimal place) and total_reviews(). These methods are callable directly in templates ({{ property.average_rating }}) on both property cards and detail views, ensuring instant recalculation whenever a review is posted or modified.
Q28: How does unique_together prevent duplicate reviews while allowing review updates? Intermediate
Answer: In properties/models.py, the Review model declares unique_together = ('property', 'tenant'), creating a compound database UNIQUE index on (property_id, tenant_id). In the view add_review(), Django checks for existing records: if a review exists, it updates the record's rating and comment; otherwise, it creates a new one. This prevents review spam while allowing tenants to easily update their feedback.
Q29: What automated unit tests did you write for the Review feature? Advanced
Answer: We implemented ReviewTest in properties/tests.py containing 5 unit tests:
  • test_anonymous_cannot_review: Anonymous requests are redirected to /accounts/login/.
  • test_user_without_booking_cannot_review: Users without bookings cannot submit reviews.
  • test_owner_cannot_review_own_property: Property owners cannot rate their own listings.
  • test_verified_tenant_can_submit_review: Booked tenants submit 1–5 stars and average_rating() recalculates dynamically.
  • test_verified_tenant_can_update_existing_review: Subsequent reviews update existing rows without duplicates.
Q30: How did you solve the select dropdown styling issue on Windows dark mode? Intermediate
Answer: In Chromium/Edge browsers on Windows, native <option> elements inherit color: #ffffff from dark mode select styles, but the OS popup menu defaults to a white background, creating unreadable white-on-white text. We resolved this by adding color-scheme: dark; to :root and styling select option { background-color: #12121a !important; color: #ffffff !important; } in style.css, guaranteeing dark popups and high-contrast options across all platforms.
